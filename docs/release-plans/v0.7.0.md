# Daphne v0.7.0 release roadmap

Status: planned  
Development branch: `dev`  
Release branch: `master`  
Previous release: `v0.6.0`

This checklist is the working plan for Daphne v0.7.0. It records release scope,
acceptance criteria, and validation evidence. Checking an item means that the
corresponding change or review is complete on `dev`; it does not by itself make
the work part of a release.

## Release scope

- [ ] Add the *Homeric Hymn to Aphrodite* (`tlg0013.tlg005`) as a canonical
  primary Daphne treebank.
- [ ] Complete and document an end-to-end scholarly review of
  `tlg0013.tlg005`.
- [ ] Supply a complete, formally well-formed enhanced graph throughout the
  treebank.
- [ ] Systematically annotate ellipsis and manually review every applicable
  sentence and every enhanced arc incident on an empty node.
- [ ] Validate the treebank with a pinned release of the official UD validator.
- [ ] Define, implement, test, and run Ancient Greek validation profile 1.
- [ ] Publish the tested release from `master` and tag the exact release commit
  as `v0.7.0`.

## 1. Release and validation policy

- [ ] Treat v0.7.0 as an additive pre-1.0 release: it adds a treebank and new
  maintained validation capabilities.
- [ ] Give each validator and custom rule a stable, documented identity.
- [ ] Define `Daphne Ancient Greek validation profile 1` as the composite
  general-validation profile for this release.
- [ ] Define `Daphne enhanced validation profile 1` as the enhanced-graph
  validation profile for this release.
- [ ] Record the exact validator versions and options in maintained
  documentation and in catalog validation notes.
- [ ] Keep scholarly review, general mechanical validation, enhanced review,
  and enhanced mechanical validation as independent claims.
- [ ] Ensure that any edit to validated CoNLL-U content resets the affected
  catalog validation status to `not_run` until the complete profile is rerun.

## 2. Add `tlg0013.tlg005`

- [ ] Add the canonical CoNLL-U file at
  `data/annotation/tlg0013/tlg005/tlg0013.tlg005.daphne_tb-grc1.conllu`.
- [ ] Add one primary catalog record with identifier
  `tlg0013.tlg005.daphne_tb-grc1`.
- [ ] Use the CTS URN
  `urn:cts:greekLit:tlg0013.tlg005.daphne_tb-grc1`.
- [ ] Record the work title, source edition, source attribution, Daphne roles,
  and the exact applicable source license without inventing missing credits.
- [ ] Add or update author-level documentation for `tlg0013`.
- [ ] Add a CTS/TEI supporting edition under `data/texts/data/tlg0013/tlg005/`
  if Daphne's text, emendations, or tokenization require one.
- [ ] Enter the new record conservatively as `converted` or `in_review` with
  general and enhanced validation set to `not_run`.
- [ ] Confirm that the catalog covers the new path exactly once.

## 3. Integrate the official UD validator

- [ ] Add an exact `udtools` dependency with `uv` and commit `pyproject.toml`
  and `uv.lock` together.
- [ ] For the initial implementation, pin `udtools==0.2.8`; if a newer release
  is deliberately selected before the v0.7.0 freeze, update this checklist and
  rerun the full validation cycle.
- [ ] Use the validator and Ancient Greek data bundled with the pinned package;
  do not load mutable data from an external checkout.
- [ ] Invoke the official validator with language `grc` and validity level 5.
- [ ] Validate all files belonging to one catalog record in one run so that
  treebank-wide final checks are performed.
- [ ] Treat every official-validator incident classified as an error as
  release-blocking, at every mandatory level and in every test class.
- [ ] Report official warnings, but do not make them release-blocking in
  validation profile 1.
- [ ] Treat a validator crash or incomplete result as failure, not as a pass.
- [ ] Produce deterministic human-readable diagnostics and a non-zero exit
  status on failure.
- [ ] Add focused tests for invocation, error classification, warning handling,
  multiple-file records, and validator failures.

## 4. Implement Ancient Greek validation profile 1

- [ ] Define the initial inventory of Ancient Greek-specific rules before
  promoting `tlg0013.tlg005` to `reviewed` and `pass`.
- [ ] Limit profile 1 to errors; do not introduce a scholarly-warning severity
  in this release.
- [ ] Assign every rule a stable identifier and document the annotation
  assumption it enforces.
- [ ] Add a focused positive and negative fixture for every rule.
- [ ] Make every Ancient Greek profile 1 finding release-blocking.
- [ ] Accept explicit input paths and avoid hard-coded user directories.
- [ ] Keep validation non-mutating, deterministic, and safe by default.
- [ ] Provide a non-zero exit status when one or more errors are found.
- [ ] Add the maintained implementation under `code/src/`, tests under
  `code/tests/`, and declarative rules under `code/rules/` where appropriate.
- [ ] Document how to run the profile locally and in CI.

## 5. Complete the scholarly review

- [ ] Set `annotation_status: in_review` while the end-to-end pass is active.
- [ ] Document the review scope and coverage in the catalog's `review` object.
- [ ] Review tokenization, text, lemmas, UPOS, morphology, basic dependencies,
  and relevant metadata across the complete work.
- [ ] Resolve or explicitly document every known release-blocking issue.
- [ ] Preserve existing source attribution and keep source roles distinct from
  Daphne editorial roles.
- [ ] Mark `annotation_status: reviewed` only after the documented end-to-end
  manual pass covers the whole declared scope.

## 6. Complete and review enhanced dependencies

- [ ] Supply a self-contained enhanced graph in `DEPS` for every sentence.
- [ ] Ensure that the enhanced representation covers every syntactic word and
  every empty node present in each sentence.
- [ ] Check empty-node IDs, enhanced heads, relation serialization, ordering,
  graph connectivity, and other mechanically testable well-formedness rules.
- [ ] Add a Daphne whole-record presence check because the official UD format
  permits enhanced annotation to be absent.
- [ ] Inspect every sentence manually for an applicable but missing ellipsis
  analysis.
- [ ] Enumerate every empty node and manually inspect every enhanced arc for
  which the empty node is either head or dependent.
- [ ] Record the reviewed file or commit hash, review date, number of empty
  nodes, and number of incident arcs inspected.
- [ ] Set `enhanced_dependencies.encoding: complete` only after whole-record
  enhanced presence and formal well-formedness have been demonstrated.
- [ ] Set `phenomena.ellipsis: systematic` only after the sentence-level
  coverage review and empty-node arc audit are complete.
- [ ] Record enhanced provenance as `manual`, `mixed`, or another accurate
  existing catalog value.
- [ ] Set enhanced `review_status: reviewed` only after the manual audit is
  complete.

## 7. Final validation and catalog state

- [ ] Freeze the candidate CoNLL-U content before recording final validation
  dates.
- [ ] Run the maintained unit-test suite.
- [ ] Run `daphne-check` over the complete repository.
- [ ] Run the pinned official UD validator with `lang=grc` and `level=5`.
- [ ] Confirm that the official validator reports zero errors across all
  mandatory levels and test classes.
- [ ] Run Ancient Greek validation profile 1 and confirm that it reports zero
  errors.
- [ ] Confirm that the official run reports zero errors in the `ENHANCED` test
  class.
- [ ] Run the Daphne whole-record enhanced-presence check successfully.
- [ ] Set general `validation.status: pass`, with the composite validator name,
  exact component versions, options, and check date.
- [ ] Set enhanced `validation.status: pass`, with the enhanced-profile name,
  exact component versions, options, and check date.
- [ ] Rerun the full affected profile after any subsequent CoNLL-U change and
  update the recorded dates only from the final successful run.
- [ ] Report basic well-formedness separately from scholarly and UD-level
  review in the release notes.

## 8. CI and repository integration

- [ ] Make validator unit tests part of the required GitHub Actions job.
- [ ] Decide whether corpus-wide Ancient Greek validation runs on every push,
  on pull requests, or only in the strict release job.
- [ ] Keep ordinary development usable: validator implementation tests may be
  mandatory even when known corpus findings remain advisory outside the
  release profile.
- [ ] Add `dev` to the GitHub Actions pull-request branch filter if feature pull
  requests will normally target `dev`.
- [ ] Keep `master` unchanged until an authorized, tested release merge.

## 9. Release preparation

- [ ] Update `README.md` with the v0.7.0 highlights.
- [ ] Update the project version in `pyproject.toml` and
  `code/src/daphne_treebank/__init__.py` to `0.7.0`.
- [ ] Update `data/STATUS.md`, `data/catalog.schema.json`, catalog records, and
  focused tests together if release work changes status semantics or schema.
- [ ] Review the diff from `v0.6.0` for accidental generated files, editor
  artifacts, large validator output, or unrelated changes.
- [ ] Confirm that `AGENTS.md` remains ignored and untracked.
- [ ] Decide the disposition of this working checklist before the release
  merge:
  - [ ] preserve it as a completed historical record on `master`; or
  - [ ] distill its outcomes into permanent release notes and remove the
    working-plan file on `dev` before merging to `master`.
- [ ] Run the final required commands:

  ```bash
  uv run python -m unittest discover -s code/tests -v
  uv run daphne-check --root .
  ```

- [ ] Run the complete general and enhanced release validation profiles.
- [ ] Confirm that the working tree is clean and all intended changes are
  committed on `dev`.

## 10. Publish v0.7.0

- [ ] Open or prepare the release merge from `dev` to `master`.
- [ ] Confirm that the release candidate commit passes all required GitHub
  Actions checks.
- [ ] Merge the tested release commit into `master` without introducing
  release-only data changes after validation.
- [ ] Confirm that GitHub Actions passes on the resulting `master` commit.
- [ ] Create the annotated tag `v0.7.0` on that exact commit.
- [ ] Push the tag and create the corresponding GitHub Release with final
  release notes. GitHub releases are based on tags and publish an archive of the
  repository at that tagged point.
- [ ] Verify that the published tag, GitHub Release, catalog statuses, package
  version, and documented validator versions agree.
- [ ] Align `dev` and `master` at the release point, then resume ordinary work
  on `dev`.

## Definition of done

v0.7.0 is ready only when `tlg0013.tlg005` is present under its canonical path;
its scholarly and enhanced reviews are documented; its catalog metadata matches
the final content; the structural, official UD, Ancient Greek, and enhanced
profiles all pass; the repository-wide required checks pass; and the exact
tested commit is published from `master` and tagged `v0.7.0`.
